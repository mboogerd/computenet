# 03 Execution model + durability assessment

## Summary
1. The kernel execution substrate (ManagedHost, colors/schedulers, intake open/saturated/closed, drain/resume/migrate, WAL + I-7 recovery) is ONE canonical implementation, not parallel copies. Partitioning is one model (PartitionedCell = degenerate placement of PartitionedShardSet).
2. Mobility is in-process only: `migrate` hands the live cell object to the target host (ManagedHost.kt:1787-1800); every test/concord migration targets a host in the same JVM. Cross-JVM migration does not exist and is untracked.
3. Durability is a uniform host-level opt-in (journal / journalFor / journalForPort) but recovers frames only. It has no topology/structure log, so every durable demo rebuilds its graph by hand. Three demos bypass it entirely with their own JSONL journals. This is tracked (computenet-6aj8h, 8xstm).
4. There is no shared runtime bootstrap. 14 demo mains construct ManagedHost/registry/journal/peering themselves. Budget is vocabulary with no charging, placement is research-gated, and no demo configures intake bounds.
5. The composition probe (exchange) proves wire+replication+partition+glitch-free in one graph. Durability, host migration, promotion and budget are each tested in isolation, never combined in one graph.

## Bridging proposals (ordered)
1. (M) Land the topology journal (8xstm) as a kernel StructureLog, generalizing KeyedCells' key log to spawn/link/unlink records, so `recoverFrom` rebuilds the graph. Then migrate backlog-triage, alignment and allocator-observe off their bespoke journals (S each).
2. (M) Add a `Runtime`/`Node` bootstrap in kernel or a thin module that builds the host tree, registry, optional journal+StructureLog, optional WsTransport peering and optional inspector from one config. Port exchange and shopping first, then the rest.
3. (L) Cross-JVM migration: a state-transfer frame (snapshot + cell factory id from the generated descriptor + parked invocations) over the wire, with a remote `spawn` on HostManagementApi. File an epic. It depends on proposal 1 (the structure record is the relink plan).
4. (M) Extend the exchange composition probe (or add a sibling) with a journaled shard host: crash+recover and host `migrate` inside the same graph, over 100 seeds. Add concord scenarios that combine dur with dist (a durable cell migrated then recovered, and a durable replicated shard).
5. (S) Once ECO1 F3 lands, have the bootstrap from proposal 2 install the ledger by default, and let one demo configure intake bounds plus a budget ceiling so saturation and denial appear in the UI.
6. (S) Add :bench fixtures for journal append/replay cost and migrate latency, which the PLC cost model (gated on BEN2) will need anyway.
